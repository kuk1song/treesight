# treesight design

The single source of the design. Change the design here first; where the code and this file disagree, the author's latest decision wins and is written back here. Last revised: 2026-10-27 (fixes from a code review).

## 1. The problem

- With many sessions it is hard to recall what a session did, what it established and what is still open. Claude Code has a session list, `/recap` (the current session only, in one sentence) and the status views listed below, but no local view that brings together, across sessions, what each one did and what remains.
- Similar tools (checked on 2026-10-15 against each repository's own description and the official docs):
  - Browsing, statistics or replay without a model: ccusage, claude-code-log, claude-code-history-viewer, ccresume, claude-history, claude-replay, bough. The official `/insights` gives an overall usage report; agent view, the desktop sidebar and Projects show whether a session needs you now, is running or is done, and Projects' "Waiting on you" covers cloud threads only.
  - Extracting sessions with a model: claude-mem, alluvia (decisions with quoted evidence, and unresolved questions), context-visualizer (typed milestones), thoughtdag. Whether agentsview (local search, statistics and insights) and wayfinder (goals, attempts, branches and results drawn as history) use a model is unverified.
  - Tracking loose ends: loose-ends (proposes closing an item with a quote, for you to confirm), openloops (what is owed and blocked, from GitHub issues), the official productivity plugin (`TASKS.md` plus a local board).
  - treesight sets out to combine three things that none of the tools checked does together: sessions extracted into nodes by "is it over, and who moves next", drawn as a session tree and a project view; open items listed across sessions with who they wait on, for how many days, what is overdue and what blocks what; an append-only ledger (section 4).
- Judgement: recalling past decisions is a real need; the tree is the means, not the goal. The name and the features serve "recall at a glance, and know what is left".

## 2. Classification: two questions

1. **Is it over?** What is over goes on the trunk, in two kinds only: **done** (decisions included; something that got stuck but worked out counts too, labelled by its result, with the bumps in its story; fixed but not verified does not count) and **found** (something established).
2. **If not, who moves next?** **To do** (you) and **waiting** (on someone else, or put off on purpose); together they are the **open items**.

Basis: an internal test of 13 sessions, 117 moments and 44 open items, labelled independently by two models. Two classes agreed 90.6% (kappa 0.79); the earlier four classes 84% (0.76); five classes 81% (0.73); open items 75% (0.59). Two classes were chosen mainly because they are easy to understand; the differences in agreement are within error.

Rules:
- ↺ An overturn can hang on a done or a found node; hovering draws a dashed line to the overturned node and strikes it through.
- Consecutive events of the same kind become one node, which says "N related events merged here" on hover; of a chain of cause and effect only the step most worth recalling is drawn.
- A one-off instruction is not an open item.

## 3. The page

### Shapes and colours

Every colour difference also has a shape difference (WCAG 1.4.1): done is a filled circle, found a four-pointed star, getting stuck leaves a scar ring on the branch, to do is a hollow ring, waiting a dashed ring, overdue a filled red dot.

### Session view

- A central trunk with nodes alternating left and right, newest at the top and the root as the start. Labels have at most 8 units (one CJK character or one word counts as one unit); hovering shows one sentence; clicking expands the node into one panel beside the trunk, its text flush left on both sides (text aligned to the trunk had a ragged left edge, which USWDS and typography guides advise against for more than one line): a story's three rows if it got stuck, else the sentence, then the twigs as a list. After the sentence or a twig that a quote supports there is a small "quote" mark; a click shows under it who wrote the quote, when, and its words, with Markdown's bold and code drawn as such. The author chose this on 2026-10-23 over a time after every twig (2026-10-21), which repeated one time when all the quotes came from one reply and showed raw text out of context: summary products show a source on request rather than inline (Notion's and Linear's citations on hover, Google Meet's timestamps that open the transcript), NN/g found that people rarely click citations, citations raise trust even when they are random (Ding et al., AAAI 2025), and every quote is already checked against the transcript when the ledger takes it. The panel shows the sentence (for a node that got stuck, the three rows stand in for it): the hover card is hidden on an open node, and #17 also hid the sentence in the panel whenever a mouse was in use (fixed 2026-10-23; `dev/check_live.mjs` checks it with a mouse). On narrow screens the card slides up from the bottom; focus is outlined. Each branch ends at its node's dot: the dot sits on the title's first line and the branch's tip at its centre, 3 px short of it (before 2026-10-26 the tip was 7 px above the dot of a one-line title, 20 px for two lines, and 10 px away, which the author noticed; NN/g on connectedness: things joined by a line read as one, so a line that misses reads as a mistake). `dev/check_live.mjs` measures it in a browser.
- Default nodes: the top min(9, node count) by score (ties to the newer), drawn in time order, with no kind forced in. With 9 nodes or fewer, all are shown and there is no "Show all". The node count comes from extraction and grows with the session.
- Why time order: Parnin and DeLine (CHI 2010) found that automatic cues doubled the rate of successful resumption after an interruption compared with notes alone, and that people preferred cues in time order.
- "Current" after the title marks the session you are in.
- Under the title, what the last run changed, unless that is everything shown (a first run's counts are the totals above it; dropped there on 2026-10-23). What the model noted it was unsure about stays in the ledger and is not shown: from 2026-10-21 to 2026-10-26 "What this run was unsure about ▸" opened it there, but such notes were mostly judgement calls rather than doubts, a label about doubt cast it on the whole tree without pointing at any item (uncertainty helps when it is specific: Vasconcelos et al., ToCHI), and the author found the line noise (2026-10-26).

### Crown

- One button only, "N still open ›", with "· N overdue" when due dates have passed and "· N no longer possible" when the model judged items can no longer be done; opened, its arrow turns (‹), and a second click closes it (it said "· Show timeline ▸" until 2026-10-23).
- "Just done" was dropped: it repeats the first node on the trunk.
- "Next step" was dropped: it is the plan the agent wrote at compaction time ("Optional Next Step" in the compaction summary), not something the user has to handle; it goes stale fastest, yet it took the largest icon on the page, against visual hierarchy (NN/g: the most important is the largest). Reminders on returning to a session are left to Claude Code's own recaps and `/recap`.
- Finished items are not listed (GitHub, Apple Reminders, Linear, Things and agent view all hide or sink them).

### A node that got stuck

- The scar is coloured by how long it was stuck: under 1 hour grey brown, 1 hour to 1 day mid brown, over 1 day bright orange (after Statuspage availability bars). When the duration is uncertain, the known lower bound is drawn.
- Opened, it is a small timeline of three rows of equal height, "Stuck / Response / Result", each row with its time and the total duration first (after Google SRE postmortem timelines); the row icons are the scar ring, a small grey dot and the done circle; a temporary workaround gets a "Temporary" tag (the PagerDuty template separates temporary fix from long-term solution, and 8D separates interim from permanent actions).

### Open-items drawer

- A drawer on the right titled "Still open", stating its scope (this session, or the N sessions with a tree in the project) and today's date; one column with the axis on the left.
- Sections come from the data: overdue (past the due date) and no longer possible first, named "Overdue or no longer possible" when both occur; then "To confirm" (the model thinks it is done but is unsure); then "With a due date", soonest first, each row giving the date and the days left (before 2026-10-21 these fell under "No time set" and showed their date only once it had passed); then one section per time label found in the data; last "No time set". Only sections with items appear.
- Within a section: items the extraction ranked come first, the newer session's first, since ranks are given within one run of one session (two "1"s from different sessions used to sit side by side; changed 2026-10-21), and waiting items keep their rank too; then a "Below, in the order raised" divider; items waiting on others come last and say who they wait on ("Put off" when no one is named, meaning you put it off yourself), since when and for how many days (after Todoist's @waiting_for and Things' tags); an item blocked by another says "Needs your “…” first", and hovering or focusing either one highlights both.
- Overdue items say "N days overdue"; items that can no longer be done say "No longer possible · close it?", and such an item counts as no longer possible even when its due date has also passed (the crown count, the section name and the row agree; before 2026-10-20 the crown counted it as overdue). The axis is not ordered by when items were raised, and older items do not fade (that would hide the oldest); items without a date are not placed as if near or far.
- Everything is listed, not only the first few (there is no firm basis for "show 3").
- Clicking an item shows its sentence, the session it came from, and a quote mark as on a node.

### Project view

- One dot per session, larger with more prompts (labelled "N prompts"); the current session is a white dot and the others grey (white to grey 3.26:1, grey dot to background 4.83:1), and screen readers say "Current session". The current session is the conversation that last ran treesight and is listed: a run started from the page's link runs in a new conversation that holds only the command and is not listed, so the white dot stays on the conversation the user came from (decided 2026-10-26; before, no session had it after such a run). A session without a tree is a grey ring instead, and once some session has a tree while others have none, a line under the crown says which mark is which, with counts ("● With a tree 1 ○ No tree yet 14"; the author chose it on 2026-10-23 from four versions tried on real data). The page shows the project's name, with its path on hover.
- Pointing at or focusing a session draws a ring around its dot in 0.35 s; hovering adds no grey background.
- A session with a tree has "›" after its name and is a link straight into its tree; hovering it shows its overview, marked AI, and how many nodes and open items it has (Apple HIG: a disclosure indicator for drilling down; Shneiderman 1996: overview first, details on demand, with a way back). A session without a tree says on hover "No tree yet · click for the session overview" when it has an overview, "No tree yet · overview being generated" while a run writes it, and only "No tree yet" otherwise (until 2026-10-26 it offered a summary also when there was none, as on every first run; NN/g: an empty state says what the system is doing, and a tooltip stays brief and true). Clicked, it shows its overview, marked AI, or says that it is being generated or comes with the next run that draws a tree, and two links, "Draw the tree" and "Open the session", which open Claude Code in a new terminal with `/treesight:treesight <id>` or `/resume <id>` typed in (its `claude-cli://open?cwd=…&q=…` deep links, https://code.claude.com/docs/en/deep-links; nothing runs until Enter). "Draw the tree" adds `--no-open`: the page is open, so the new conversation's run updates it rather than opening another tab (each conversation otherwise opens the page once). Every browser asks before it hands such a link to an app (Chrome asks whether to open "Claude Code URL Handler" on every click unless "Always allow" was ticked; Safari and Firefox ask too, as guides to joining a Zoom meeting from a browser show), and a page cannot turn that off (Chromium's `external_protocol_handler.cc`, read 2026-10-28; only an enterprise policy can). Since 2026-10-29 (the author had not understood that prompt at first, section 6, "Seventh interactive test") a line under the two links says it before a click: the browser asks first, choose Open or Allow, and the command waits in a new terminal until Enter (the pattern of Zoom's join page, which names the browser's button and offers another way in). The page does not suggest ticking "Always allow": Chromium remembers it per initiating origin and scheme, and every page on disk shares the origin `file://`, so it would let any local HTML file open a terminal with a prompt typed in. A link can also do nothing (Claude Code registers the handler on the first interactive prompt, and a setting turns it off), so after a click the line says "Choose Open or Allow in your browser’s prompt. Nothing opened? Copy the command", in a status region that screen readers announce; for "Open the session" the command is `cd <the whole folder, quoted> && claude -r <id>` (a `~/` shortcut guessed from `/Users/<name>/` would point into another user's folder). When part of the folder's name was masked as an address or a secret, the page offers only the command to copy, since a link to the masked folder would point nowhere; the project's name is masked like its path (the author chose this on 2026-10-23 over a copy line shown at rest; where the browser refuses the clipboard, the command is shown selected instead). How far the links were tried is in section 6 ("Seventh interactive test"). Until 2026-10-21 hover and click showed the same text, against the guidance that a tooltip is brief and that opening something shows more, not the same (Carbon, Primer, Microsoft).
- The project's open items come only from sessions with a tree, which the line under the crown shows; it replaced "Only the N sessions with a tree, of M" on 2026-10-23, which the author found hard to read. Before the first tree exists the crown is not shown at all: it used to say "Nothing left open" and "From 0 sessions with a tree", a false zero (NN/g lists announcing that there is nothing, then showing content once a process ends, as a common mistake).
- A session is named by the user's own title, else by the generated one. Its overview (会话概况 in Chinese, chosen by the author on 2026-10-26 over 摘要, which did not say how it differs from the tree) is one sentence a treesight run wrote (section 4, "Summaries"). Before 2026-10-23 it was Claude Code's latest automatic recap, else its first prompt that is not pasted output: on the author's project the last recap of 8 of 12 Chinese sessions was in English (the docs do not say which language recaps use), some kept the hint "(disable recaps in /config)", recaps say where a session stopped rather than what it was about, and first prompts were often pasted text or a nudge to continue. Sessions whose every prompt came from `claude -p` or the Agent SDK (scripts and tests) are left out unless drawn, and the footer says how many.
- "Open the session" was added on 2026-10-23 at the author's request; there was no such button before, as the official `claude --resume` picker copies the `cd` and resume command itself for a session of another project, and `--resume <id>` works in any directory since 2.1.223. Resuming a session that is still open in another terminal interleaves writes into the same transcript (code.claude.com/docs/en/sessions: "messages from both interleave into one transcript"), so the link only types the command and leaves Enter to the user. The only thing a tree could add is "fork from this node", publicly supported only by the Agent SDK's resumeSessionAt; extraction already stores each node's message id, leaving room for it.

### Navigation

- Hash routes: `#p` is the project view and `#s=<first 8 characters of a session id>` a session; without a hash, the page shows the session this build is about, else the current session, and the project view while that session has no tree. Reloads and bookmarks land on the same view, and the browser's back button works (NN/g: the back button is the user's lifeline).
- Back to the project: a vertical tab "Whole project" on the left edge, without an arrow, that slides out a little on hover; in a window narrower than 1020 pixels, where the tab would cover the tree, it becomes a button at the top left on its own line above the legend, with an arrow (‹), so it does not read as one of the legend's items (changed 2026-10-20; it used to share the legend's row). Going back after coming from the project pops the history instead of pushing another entry. With only two levels, there is no full breadcrumb (NN/g).

### Legend

Only shapes on the current view are listed: the project view's legend is the line under the crown, shown once some session has a tree while others have none; the session view lists done, found and scar for the nodes shown; the drawer lists what its list contains (to do, waiting, overdue).

### Motion

- Each view grows its tree upward from the bottom of the visible area (in a short window the root is often below the fold). The first time a set of data is seen it takes 1.0 s; after that, reloads, entering the project or a session, going back and the back button take 0.6 s; "Show all" grows only the added nodes, in 0.45 s. The whole sequence is scaled so that its last piece ends at the target time.
- The tree also grows on a page opened while a run is drawing (from 0.1.0 such pages stood still, as they reloaded every 20 s; the author missed the growth on 2026-10-22), and growth waits until the tab can be seen, so a tab opened or reloaded in the background grows when it is first shown (browsers stop animation frames in background tabs, MDN, Page Visibility API).
- A click or any key during growth finishes it at once; with reduced motion requested there is no motion; "already seen" is kept in the browser's local storage.
- Basis and trade-off: NN/g recommends 0.1 to 0.5 s for most interface animations, shorter the more often they are seen, and Apple HIG advises little motion for frequent actions; growing on every view is the author's request, and 0.6 s with a skip at any time is the compromise. Measured by the author in a real browser: entering a session took 3 ms to render plus 0.61 s of growth (0.60 planned).

### Theme, colours and language

- Dark only for now: the page declares `color-scheme: dark` and does not read the system setting, and the footer says "Dark theme only". This is a scope choice, not best practice: NN/g finds light mode better for normal vision and recommends letting people switch, following the system by default; WCAG does not require a light mode. Light colours stay in `dev/palettes.json`, to be redone separately rather than inverted mechanically.
- The single source of colours is `dev/palettes.json`; `templates/page.html` has the same values hard-coded and a unit test keeps them in step; `python3 dev/palcheck.py` checks 4.5:1 for text (on the background and on the drawer) and 3:1 for shapes.
- Chinese text the model wrote (overviews, labels, lines, twigs, stories) is shown with full-width `，；：！？（）` where they touch Chinese, as the page's own words have: in the run of 2026-10-24, 81 of 82 such marks were half-width. Quotes, code in backticks, times and addresses stay as written. The extraction guide asks for them too.
- Language comes from three places. The interface text, in Chinese or English, follows the first of the browser's preferred languages that is one of the two, and English when neither is listed (before 0.1.1 only the first preferred language counted, so a browser preferring Japanese, then Chinese, showed English). Chinese is simplified Chinese, also for `zh-TW` and `zh-HK`. Extracted text stays in the session's language: the model writes labels, lines and stories in the language most of the user's prompts are in, helped by the digest's header, which counts the prompts containing Chinese characters in each pass. The report in the conversation is in the language of the session's prompts. A Chinese session can therefore appear in an English interface, and the other way round.
- The tab icon is logo sketch B on a dark rounded square, as inline SVG (chosen by the author on 2026-10-16), with no light and dark media queries because Safari 26 ignores media queries in SVG icons (WebKit bug 309949); the earlier transparent version left the trunk nearly invisible in light Safari. The README shows the same mark as `docs/logo.svg`, with a thin border for GitHub's dark theme; it animates once (the timings are in the file's comment) and stays still when reduced motion is requested.
- Current colours (the `default` scheme in palettes.json): done #C8FF00, found #FFD60A, to do a hollow ring in the same green, waiting #6E6F74, overdue #FF6F61, scars #9C8167 / #C48A5C / #F0A060. Every shape is at least 3.6:1 against the background. Risk: on dark, done and found differ by only 0.034 (OKLab) for green-blind viewers and are told apart by circle and star.
- The public version keeps this palette (author's decision, 2026-10-16), to be redone later; a "signal" candidate from 2026-10-06 (the past all grey, blue and vermilion, at least 0.237 apart under three kinds of colour blindness) was tested on the earlier classification and needs remapping before use.

## 4. Data and extraction

- **Everything comes from the transcripts** (`~/.claude/projects/<project>/<session>.jsonl`): automatic recaps, compaction boundaries and summaries, every prompt, generated and custom titles. The official docs say the format is internal and may change in any release, so all reading is in one adapter. Transcripts are kept for 30 days by default (`cleanupPeriodDays`), so rebuilding from transcripts alone would drop old sessions from the page. The page therefore relies on the ledger: extraction stores each session's title, start and end times and prompt counts with the run, and the page draws the transcripts on disk plus the sessions in the ledger; a session whose transcript was cleaned up is still shown, marked as such. Before 2026-10-16 the page read only the transcripts on disk, so a cleanup removed the tree and its open items too.
- **No full regeneration each time:** model output is not deterministic (official: even temperature 0 is not fully deterministic, and newer models do not allow setting it); in an internal test the same session extracted twice gave 9 nodes once and 18 the other time, with only 4 clearly matching. So:
  - Results go into a local append-only ledger. What is generated is frozen, each session remembers how far it was read, and only new content is extracted. An ongoing session is frozen as far as it was read; things still open at that point become open items, which later runs can only close.
  - The model can only add, or close an existing open item by its id with a quote (when an earlier session is drawn after later ones, it can also close its own new items with the later records, see "Drawing order"); unsure closes go to "To confirm" and are not applied. "No longer possible" and "done" are recorded separately.
  - The user's own changes are a separate layer and always win. Starting over (when the user asks or the extraction rules change: compute a second version, show the difference, switch only on approval, keep the old one) is not implemented.
  - The page is drawn from the ledger by a script; a run with nothing new still takes a few short model requests (18 to 44 s in testing) to prepare and redraw. Under a session's title it says how many nodes and open items the last run added, how many it closed and how many it left to confirm; a run read in two passes counts as one (since 2026-10-21; before, the second pass replaced the first there, so the page showed only its counts, and the first pass's notes were lost once the report stopped listing them). The last two count after the user's changes (items the user reopened, closed or hid count as neither), so they match the list on the page; before 2026-10-19 both were merged into "N closed", which did not match. Because the user's changes always win, an item the user reopened stays open even if the model closes it again later.
  - **Drawing order** (changed 2026-10-19): a close can only name an open item already in the ledger, so when a later session was drawn first and an earlier one afterwards, things the later session had finished came back as open (another agent, Codex, reproduced this with the made-up project: 6 open in time order, 8 in reverse). Now, when an earlier session is drawn, the digest's header lists "later records": other sessions' nodes and model closes from after the digest starts, each with a quote checked when it was recorded (closes the user rejected with `reopen`, and hidden nodes and items, are left out; at most 40,000 characters, keeping the newest). The model lists the new items they settled under `settled`, naming only the item and the record, and the ledger records a close with that record's own quote; unsure ones still go to the user. Drawn in time order, the header has no such section, as before. Still not covered: a later session's node overturning an earlier session's node, and things a later session finished without recording them as a node or a close.
  - Time checks on closes (added 2026-10-19): the ledger refuses a close whose quoted message is earlier than the item was raised (a date without a time counts from that date's start in UTC+14, so a time zone cannot block a same-day close), and a close's time must be its message's time (not checked before). Open items raised after the digest starts have their raised time in the header.
- **The digest keeps texts whole** (changed 2026-10-16): prompts, replies and the assistant's text within each turn reach the model in full. Only two things are shortened, and the header says so: pasted blocks keep their first 400 characters, and compaction summaries are cut to 8,000 characters by section priority (they restate earlier messages, which are all in the transcript). Sections are found by their numbered headings, also when written in Markdown (`1. **Pending Tasks**`, as 2 of the 8 summaries in this project's own transcripts were on 2026-10-27; until then those were cut from their end, to-do section first); a summary whose headings are not found keeps its first two fifths and its end.
  - A digest holds 150,000 characters by default. More is read in passes, broken at turn boundaries where possible, and each pass is recorded before the next continues from there. One run reads at most two passes and reports what is left, and the next run goes on, so the subagent's context stays bounded. A second pass is read only for content that did not fit when the run was prepared; what the user writes during the run waits for the next run (before 2026-10-20 it caused an extra pass). Only an entry longer than a whole pass is cut, and the header says how many were.
  - Before the change, every prompt and every turn's last reply kept only 1,500 characters and other replies 500, while the header said nothing was cut. In an interactive test a real 8-prompt session lost 8 open items this way (its digest used 13% of the limit).
  - treesight's own traces are not new content: the message that invoked `/treesight`, and the main conversation's turn that its completion notice starts. Otherwise every run in the current session would find new content the next time and record the main conversation's retelling of the report as session content. That turn ends at the next user record that starts a turn (a prompt, a slash command, another notice). A line in a session that happens to look like a digest entry header gets a leading space, so it is not taken for a new entry.
- **Summaries** (added 2026-10-23): each session's one sentence on the project page is written by the model. The session a run draws gets it from the whole digest (`gist`, on the run's record). The first pass of a run also lists the project's other sessions that need one, at most 30, the most recent first: sessions without a tree whose summary is missing or older than their last message, and drawn sessions that have none. `show others` prints a short excerpt of each (the title, the first two and last two prompts that are neither a nudge nor pasted output, the start of the last reply and the last recap, each with its date; scrubbed like a digest; about 1,500 characters, up to 4.5 KB of UTF-8 in Chinese), in parts like the digest, and the model writes one sentence each (`others`). Which sessions were listed is kept in a work file beside the digest, not in the run's mark, which can expire before the run applies. The ledger takes summaries only for the sessions listed, each at most 50 units, as events of their own. A summary from the session's own run always wins: a later run's summary from an excerpt never replaces it (two runs at once each list the other's session; found in review on 2026-10-23). A session's last entry, not a later `/treesight` command or notice in it, decides whether its summary is out of date, so the conversation that runs treesight is not summarized again every time. The estimate adds 6 s per session to summarize. Summaries are not checked against quotes, so the page marks them AI. This sends short excerpts of a project's other sessions to the model as well (README, Privacy). On the author's project, 15 summaries an opus subagent wrote from these excerpts were all in Chinese, 32 to 39 units.
- **Data formats** (settled 2026-10-12, written as JSON Schema under `schema/` on 2026-10-16): nodes and open items have stable ids, and the ledger and the page match by id, not by title text; times are stored in full with the year and shown in local time; sessions are referenced by id, not by title (titles can change).
  - The model hands in one extraction output per pass (`extract.schema.json`): new nodes, new open items, proposed closes of existing open items, and which new items later records already settled (see "Drawing order"). New entries use temporary refs such as `n1` and `o1`, and the ledger assigns ids. Each carries its message id and one to three quotes; a script checks that each quote appears verbatim in that message (tolerating only whitespace and ellipses at either end) and that times and ids match, and records nothing otherwise.
  - The page reads each session's state (`session.schema.json`): metadata from the script plus the nodes and open items rebuilt from the ledger with the user's changes applied. Open items have three states: open, to confirm (the model thinks it is done but is unsure), and no longer possible. The schema allows items without a quote (`by: user`, reserved for items added by hand later); there is no command to add items yet.
  - A node's quote may name the twig it shows (`twig`, counting from 0); the ledger refuses an index past the node's twigs and drops the field from open items, which have none. Quotes from the node's or item's own message are stored first, since the first is the one later sessions are shown.
  - Label, line and twig lengths are counted in units (one CJK character or one word) and checked by a script (`scripts/schema.py`, standard library only). Twigs may have 16 units since 2026-10-23 (10 before), written as phrases that make sense on their own a month later: at 10 the model wrote telegraphic phrases, without subject or verb, that the author could not follow on their own project, and Microsoft's style guide and the US federal plain language guidelines warn against dropped words and noun stacks. In a run with the new rule the same details named their subject and source. Trees already drawn keep their twigs, since the ledger never rewrites.
  - "Blocked by" can name only one item; in testing the model pointed out a release waiting on two things, so it may allow several later.
- **On demand:** the session a command runs in is the one drawn, and other sessions are named by id or by words from their title (an id prefix of 8 characters or more finds a session of any project, a shorter one only of the current project, so a number such as 8080 in a title is not taken for another project's session; title words count as one phrase, else each word anywhere, and when several sessions match, the message lists their titles; items to correct are found the same way by their labels); the project list is built from metadata by a script, without a model. A static page cannot call the model, so for a session without a tree it can only open Claude Code with the command typed in, or offer the command to copy (section 3); a page that is open then updates itself. After the command, the background subagent's second step opens the page (in 6 interactive runs on 2026-10-16 and 2026-10-19, 5 opened it 7 to 12 s after the command; 1 took 205 s because the subagent's first reply broke off mid-stream and Claude Code asked for it again). The page first shows what is already known and, at the top, a pill as wide as its words: "Drawing a tree", and under it "Session “…” · about N min · updates itself when done", beside a small tree that grows, rests and grows again, every part on one 4.2 s cycle so each round starts from nothing (the author chose it on 2026-10-26 from versions on real data, over the light running round a 940 px line chosen on 2026-10-21, which looked unbalanced and whose pause mark read as pausing the run; Apple HIG: keep a progress indicator moving so the wait does not look stalled). It stops once the run seems to have stopped, so it never moves for a run that has died, and under reduced motion; a pause button shows on hover, keyboard focus and where there is no hover (WCAG 2.2.2: motion lasting over 5 s beside other content can be paused, and a loading animation is exempt only while the page cannot be used). Then it shows the result. NN/g recommends showing a percentage for waits over 10 s, but a static page cannot see extraction progress, so it gives an estimate (fitted on 2026-10-16 runs with no effort set: 120 s plus 3.5 s per 1,000 digest characters; with effort fixed at xhigh, the made-up sessions took 0.8 to 1.3 times the estimate, the 73-prompt session about 1.0 times, and an 8-prompt session with unusually long output 2.7 times).
  - Each run in progress leaves a job mark in the plugin's data folder. The page says a run may have stopped once it is 20 minutes past its estimate (a second pass does not restart the clock; the estimate covers the whole run); running the command then says the session is still being drawn if that run touched its mark in the last 20 minutes, and otherwise treats it as stopped and starts again. A run the user stopped can be started again at once with `--restart` (added 2026-10-21; before, the session stayed blocked until 20 minutes past the estimate). If that run was in fact still going, the two share the session's work files, and the ledger records only the first to apply (it accepts a digest only if it starts where it stopped reading that session); the other stops with an error, and the skill then only rebuilds the page. When several sessions of a project are being drawn, the page lists them all and says so until all are done; it opens on the session this run draws. Reading the job marks and the ledger and writing the page all happen under the project lock, so of two builds at once, the one that read the older state never writes last (before 2026-10-19 there was no such lock, and Codex reproduced, with a controlled interleaving, an older page replacing a newer one, with the drawn tree gone for a while and "Drawing" never clearing). Without `--restart`, running the command for a session already being drawn does not extract again; it only rebuilds the page, and asks the browser to open it if this conversation has not. Official: invoking a skill that is still running runs the second invocation in the foreground, and the main conversation waits for it.
  - **One page, kept current** (changed 2026-10-21; the author's first real use opened a new tab on every run): every build also writes a one-line stamp next to the page (`<page>.stamp.js`, naming the build, the session it is about and whether a run is going on). The open page loads the stamp every 2 s while a run is going on and every 5 s otherwise, also when hidden (browsers slow hidden pages to once a second, or once a minute after five minutes, so most reloads happen out of sight), and at once when it is shown again. When the stamp names a newer build, the page reloads: when a run of another session starts, or a run ends, it opens as a fresh page would, on that session; otherwise it keeps its view (written into the address first, since a page opened without one would come back on another session) and where it was scrolled to, without growing the tree again. If three reloads in a row do not bring the build the stamp names, it gives up on that build (a newer one is tried again), so a stamp and page that disagree cannot loop. Before, a page being drawn reloaded every 20 s, which also sent screen readers back to the top each time (WCAG F41). The browser is asked to open the page only on the first build of each conversation, and again when that conversation has not updated it for three hours (a conversation resumed days later keeps its id, and its old tab is likely gone); later runs and corrections update the open page, and the report gives the page's link, which reopens it if it was closed. Dev servers do the same over a connection (Vite and webpack-dev-server open the browser once and then reload or update the page); a static page cannot listen, so it polls a file. Whether a page is still open cannot be detected: a static page cannot write anything, and reading a file updates its access time only on the first read after a change (tested on macOS 2026-10-21), so the rule is per conversation. Checked end to end in headless Chrome by `dev/check_live.mjs`; Safari and Firefox are untested.
- **Privacy and security:** the page makes no network requests and is locked down by a Content Security Policy (`default-src 'none'`, the page's own script allowed by hash only, images only inline). A page built on the user's machine adds `'strict-dynamic'`, under which scripts that the page's own script inserts may run too, whatever their address (CSP Level 3 ignores address lists then), so what keeps the page offline and limited to its stamp is that its script inserts only the stamp next to it; `'self'` would have matched every local file in Chrome and WebKit and none in Firefox (their source code, 2026-10-21). Published pages, such as the sample, keep the plain policy. Common secret formats are removed before extraction (and again from what the model wrote, before the ledger keeps it; added 2026-10-27), and before any text is cut (pasted text, compaction summaries and the session line used to be cut first, so a private key cut in half no longer matched its pattern and its first lines reached the digest and the page; fixed 2026-10-21), including assignments whose name contains token, password, secret or api key (such as `DB_PASSWORD=…` and `"password": "…"` in JSON; the review before publishing on 2026-10-20 found these had been missed). The patterns take linear time on long text without spaces (measured on 2026-10-21: the email, URL and token-name patterns, unchanged since 0.1.0, took seconds on such text, such as 5.4 s for 40 KB of "a." and 17.6 s for 88 KB of a repeated "password", and the new Discord pattern grew the same way; each is now bounded or anchored, and the anchored email pattern gave the same masks as before on 200,000 random strings). The data sits in a non-executing JSON block with `<`, `>` and `&` escaped, so `</script>` in a session cannot end it. The plugin's hook (section 5) reads each prompt sent while the plugin is enabled, in memory, to find a run's completion notice, and keeps or sends nothing. The public sample page's build fails if an unmasked IPv4 address or email remains; pages built on the user's machine mask them instead (sessions often contain loopback addresses). A sample page counts days to its own date rather than the viewer's, so its numbers do not grow over time.

## 5. Delivery

- First release: one plugin whose repository is its own GitHub marketplace, with one skill that only the user triggers (`disable-model-invocation: true`). The command is `/treesight:treesight` (skills in plugins carry the plugin's prefix; `/treesight` without it also works when no other command takes the name, verified on 2.1.299).
- Extraction runs in a separate subagent through `context: fork`, leaving the user's conversation alone. Official: the subagent does not see the conversation history, so the skill body must be self-contained and the current session id is passed as `${CLAUDE_SESSION_ID}`; it runs in the background by default (since 2.1.218) and its result returns to the conversation; background subagents can use Bash and read and write files but cannot ask the user anything, so extraction never asks, and unsure items go to "To confirm".
- **Effort** (2026-10-17): the skill sets `effort: xhigh`. Without it the subagent follows the session's effort, and Opus 5.5 and Sonnet 5.5 default to medium in Claude Code, so the same plugin would differ in accuracy and time from person to person, and the README's measurements would hold only for people at xhigh. Official: `effort` in the frontmatter overrides the session's level, and only the `CLAUDE_CODE_EFFORT_LEVEL` environment variable overrides it. Measured on the made-up session with the session at xhigh and the skill at low, thinking dropped from 13,696 to 264 tokens, so the override works. The model is not fixed (it follows the session): official model aliases point to different versions on different providers (`opus` is Opus 4.6 on Microsoft Foundry), and Sonnet measured no faster (section 6). Whether to switch to high is weighed in "Effort comparison" in section 6; the author has not decided yet.
- The result returns to the main conversation as a completion notice, and the main conversation's model may start checking things on its own. In an interactive test it read treesight's files and then the user's documents, which in auto mode happens silently and spends the user's quota. So the report's first line says it is for the user and nothing else needs doing. In the 2026-10-19 interactive test the main conversation no longer called tools but still rewrote the five-line report into a longer reply, and questioned the open count with its own arithmetic (the report said 5 closes were proposed, while 3 of them stayed listed for the user to confirm). So `apply` now gives how many items were closed, how many were left to confirm and how many are open in the project, and the report stated those numbers until 2026-10-26. How the main conversation retells the report cannot be controlled, and the README says it may comment. From 2026-10-21 to 2026-10-26 the report was three lines: the fixed first line, what changed (numbers only), and the page's link with whether the browser was asked to open it or the open page updates itself. What the model was unsure about was then no longer listed there but shown on the page, under the session's title, on request (since 2026-10-26 it is kept in the ledger only): in the fourth interactive test the main conversation answered the listed points from its own context and then ran commands to check them. In the fifth (2026-10-22) it still ran 7 commands and wrote a long check of the run's notes, led there by the report's remaining line that what the run was unsure about is on the page; that line was dropped on 2026-10-23. The official docs offer no setting that keeps a forked skill's result from the main model. Since 2026-10-26 the plugin's `UserPromptSubmit` hook (`hooks/hooks.json`, `scripts/notice_hook.py`) handles it: Claude Code also runs that hook on a background subagent's report, and for a completed treesight run whose report starts with the fixed line it adds an instruction to Claude's context to reply with the report as it is, from its third line on. The report is composed by `build --done` from the run's counts, in the language of the session's prompts: a line starting with `🌳 treesight:` that says what changed (numbers that are not zero), the page's link, and a line only when something needs the user, such as items to confirm (the author chose this on 2026-10-26; clig.dev: on success say what changed and err on the side of less, emoji where they make things clearer without overdoing it; NN/g: keep users informed of what is going on). Tested on 2026-10-26 with Claude Code 2.1.299 and a throwaway plugin driven in a pseudo terminal: a forked skill's own frontmatter hook never ran, so the hook is the plugin's; blocking the notice kept it from Claude but showed the user "UserPromptSubmit operation blocked by hook:" in warning colours (with `continue: false`, "Operation stopped by hook:", and Claude saw the report later); the instruction got a reply of exactly the report, with no tools, in 3 s. Without the hook, Claude Code 2.1.299 shows only "Agent … finished · <time>" and then Claude's own retelling. The hook takes about 13 ms per prompt, lets every other prompt through, and leaves things as before when it fails or is turned off; whether Claude follows the instruction in a long session that has reviewed earlier reports is still to be seen in real use.
- **Permissions** (changed after the 2026-10-16 interactive test): the skill's `allowed-tools` has two rules, `Bash(python3 ${CLAUDE_PLUGIN_ROOT}/scripts/treesight.py *)` and `Edit(~/.cache/treesight/**)`. From the official docs: the variables are substituted only in the skill body and in `allowed-tools` Bash rules, not in Bash's environment; in Read and Edit rules a leading single slash is not an absolute path; Write rules are accepted but never used, since writes are governed by Edit rules; `~/.claude` is a protected folder whose writes no allow rule can pre-approve, and the plugin's data folder is inside it.
  - So the model reads the extraction guide, the schemas and the digest through the script's output (`treesight.py show`, in parts of at most 24,000 UTF-8 bytes: Claude Code shows a Bash result inline only up to about 30,000 bytes, measured on 2026-10-21 as 25,000 bytes of Chinese shown and 33,000 saved to a file; parts used to be 20,000 characters, and in the fourth interactive test a mostly Chinese one of 34,858 bytes was saved to a file, which the model then opened with Read), and writes exactly one file, its extraction under `~/.cache/treesight/work/` (`TREESIGHT_WORK` can move it, and then Claude Code asks before writing there). The digest and the extraction are deleted once recorded, and in any case when the run ends (`build --done`). The ledger, digest, job marks and page are mode 600, and the folders treesight creates are 700 (one that already exists keeps its mode; the extraction is written by the model's Write tool with the system's default mode, in a 700 folder).
  - In a headless run on 2026-10-23 the model once tried to fix its own output with `sed`, which was denied (in an interactive session it would have asked the user), so the skill says to fix it only with Edit.
  - Passing the JSON to the script on standard input was tried: Claude Code's safety check blocks commands that contain braces with quotes (`Contains brace with quote character`), and allow rules cannot override it.
  - Tested on 2026-10-16 with `claude -p --permission-mode default`: with these two rules nothing was denied in reading, writing, editing or applying; the old rules needed 4 to 5 confirmations per run in manual mode in the interactive test. Under `-p` the skill runs in the foreground, so the background flow and the browser are covered only by the interactive tests (section 6).
- The scripts ship with the plugin and are referenced in the skill body with `${CLAUDE_PLUGIN_ROOT}` (see "Permissions"). Pages and job marks go to `${CLAUDE_PLUGIN_DATA}` (official: kept across plugin updates, deleted on uninstall by default), all written by the scripts; the ledger and the user's changes go to `${XDG_DATA_HOME:-~/.local/share}/treesight/`, kept on uninstall and movable with `TREESIGHT_HOME`. The local page (`${CLAUDE_PLUGIN_DATA}/pages/<project key>.html`, rebuildable, with its stamp beside it) is handed to the browser on the first build of each conversation (see "One page, kept current" in section 4): with `BROWSER` set, through Python's webbrowser, which honours it; on macOS, with `open -a` and the app that opens web links (not plain `open`, which uses the app for .html files and can be an editor); elsewhere through webbrowser. The report gives the page's link; it does not say whether a tab is open. The reason is in "Third interactive test" in section 6.
- Installing (checked against https://code.claude.com/docs/en/discover-plugins on 2026-10-20): `/plugin install treesight --marketplace kuk1song/treesight` in a session needs Claude Code 2.1.275 or later and opens the plugin's details to choose a scope; `claude plugin install treesight --marketplace kuk1song/treesight` in a shell needs 2.1.292 or later, and its plugins load in the next session or after `/reload-plugins`; auto-update is off by default for third-party marketplaces. The shell form, run from an agent's Bash tool against a throwaway configuration, installed in 6.4 s with no prompt (2026-10-20).
- Claude Code only: the skill uses Claude Code's own frontmatter (`disable-model-invocation`, `context`), which the official docs say makes claude.ai uploads and Skills API packaging fail, and it reads local transcripts. An `icon` in the manifest would serve only the Anthropic directory listing (Claude Code does not read it), so none is set.
  - Where it runs (checked against the official docs on 2026-10-20; the README keeps two sentences): the Claude Code CLI in a terminal is tested. The desktop app's Code tab and the VS Code and JetBrains extensions should work but are untested: Anthropic counts them as Claude Code ("the terminal, the IDE extensions, and the desktop app's Code tab", plugin platform support), the desktop app "runs the same underlying engine" and loads user-scope plugins, and the VS Code extension shares plugins and conversation history with the CLI. The desktop app's WSL sessions load no plugins, and SSH or remote IDE sessions run on the remote machine, where the browser may not open. Cloud sessions (claude.ai/code) do not load plugins installed on the user's machine and cannot read its transcripts; Cowork takes its plugins from the claude.ai account, not from `~/.claude`; claude.ai chat rejects the Claude Code-only frontmatter. Other agents (Codex, Gemini CLI, Cursor's own agent) read `SKILL.md` but have no `context: fork` and pass no session id, and treesight reads only Claude Code's transcripts.

## 7. Tried and dropped

| Approach | Why it was dropped |
|---|---|
| Four or five classes on the trunk (decided and stuck as their own classes) | To the user a decision is done, and something that got stuck but worked out is done too |
| A minimum per class among the default nodes | Not by the facts; it forces things in |
| "Next step", "Just done" and "About to do when stopped" in the crown | See "Crown" in section 3 |
| A resume button on nodes; a legend in the project view | See "Project view" and "Legend" in section 3 |
| Dependency lines (dashed and solid arrows) | The legend did not match the drawn curves, and they repeated "First you: “…”" |
| Squares for sessions | Back to dots; the two levels are never on screen together, and project dots do not use the done colour |
| Following the system's light or dark setting | Not until the light palette is redone; see "Theme, colours and language" in section 3 |
